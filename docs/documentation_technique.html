Ce document explique comment fonctionne techniquement le site Bokonzi, depuis les notions les plus simples (qu'est-ce qu'un serveur ?) jusqu'aux détails internes (comment une recherche est mise en cache, comment le scraping remplit la base). 1 · Concepts de base (pour débutant)

Si ces mots te sont familiers, saute à la section 2. Sinon, voici les briques de base expliquées simplement.

Le modèle « client / serveur »

🍽️ Analogie : le restaurant
Imagine un restaurant. Le client (ton navigateur : Chrome, Firefox…) passe une commande. Le serveur (l'ordinateur d'Hostinger qui héberge le site) reçoit la commande, va en cuisine, prépare le plat et le ramène. Sur le web :
  • Le client demande une page (« je veux voir le profil de l'athlète n°548525 »).
  • Le serveur exécute du code PHP, va chercher les infos dans la base de données, fabrique une page HTML et la renvoie.
  • Le navigateur affiche cette page HTML.

Les langages utilisés

LangageOù il tourneÀ quoi il sert ici
PHPSur le serveurLe « cerveau ». Il décide quoi afficher, parle à la base de données, fabrique le HTML. Fichiers .php.
HTMLDans le navigateurLa structure de la page (titres, tableaux, boutons). C'est le squelette.
CSSDans le navigateurL'apparence (couleurs, polices, mise en page). Fichiers .css.
JavaScript (JS)Dans le navigateurL'interactivité sans recharger la page (ouvrir un panneau, charger des données en fond, graphiques).
SQLDans la base de donnéesLe langage pour interroger les données (« donne-moi tous les athlètes du club X »).

La base de données (MySQL)

📚 Analogie : un classeur géant de tableaux Excel
Une base de données, c'est comme un gros classeur contenant plusieurs tables (des feuilles Excel). Chaque table a des colonnes (nom, âge, club…) et des lignes (un athlète = une ligne). Ici la base s'appelle MySQL. Bokonzi a ~23 tables : une pour les athlètes, une pour les clubs, une pour les records, etc. On les relie entre elles par des identifiants (voir section 6).

Apache & XAMPP

Apache est le logiciel « serveur web » : il reçoit les requêtes des navigateurs et exécute le PHP. XAMPP est un pack tout-en-un (Apache + MySQL + PHP) que tu installes sur ton PC pour développer en local, c'est-à-dire tester le site sur ta propre machine avant de l'envoyer en ligne. En local le site est à http://localhost/BK, en ligne il est à https://bokonzi.com.

Une requête HTTP

Quand tu tapes une adresse (URL), le navigateur envoie une requête HTTP. Les deux types les plus courants :

  • GET : « donne-moi quelque chose » (afficher une page, lire des données). Les paramètres sont dans l'URL : ?page=profil&id=548525.
  • POST : « voici des données à enregistrer » (envoyer un formulaire de contact, se connecter).

JSON & API

📦 Analogie : un colis standardisé
JSON est un format texte universel pour échanger des données, lisible par PHP comme par JavaScript. Exemple : {"nom":"DUPONT","age":25}. Une API (Application Programming Interface) est une « porte d'entrée » du serveur qui, au lieu de renvoyer une page HTML, renvoie du JSON. Bokonzi a une API avec ~25 portes (les endpoints) : /api/athlete.php, /api/search.php… Le JavaScript de la page appelle ces portes pour charger des données « en fond » sans recharger toute la page.

Le cache

🗄️ Analogie : la photocopie sous le comptoir
Calculer certaines pages coûte cher (beaucoup de requêtes à la base). Plutôt que de tout recalculer à chaque visiteur, on garde une copie toute prête du résultat dans un fichier. Le visiteur suivant reçoit la photocopie : instantané. C'est le cache. Ici, les résultats d'API sont stockés en fichiers .json dans le dossier cache/ pendant 24 h (voir section 8).

3 · Cycle de vie d'une requête (du clic à l'écran)

Suivons un exemple concret de bout en bout : un visiteur ouvre le profil d'un athlète.

  1. Le navigateur demande la page. Le visiteur clique sur un lien index.php?page=profil&id=548525. Apache reçoit la requête et lance index.php.
  2. index.php se prépare. Il charge le noyau : core/paths.php (les chemins), core/db.php (ouvre la connexion $conn à MySQL), puis logIp() (journalise la visite). Il applique l'anti-scraping (compteur de pages/jour) et le minuteur « découverte » anonyme.
  3. Il identifie la page demandée. Le paramètre ?page=profil dit à index.php quelle portion afficher. Pour le profil, il appelle l'API : apiCall("$BASE_API/athlete.php?id=548525").
  4. L'API entre en jeu. api/athlete.php commence par inclure api/config.php (en-têtes JSON + connexion + auth). Il calcule une clé de cache à partir de l'identifiant, puis regarde si cache/athlete_<clé>.json existe et a moins de 24 h.
  5. Deux scénarios :
    • CACHE HIT Le fichier existe et est frais → l'API renvoie son contenu tel quel. Ultra-rapide, zéro requête SQL.
    • CACHE MISS Sinon → l'API exécute ses requêtes SQL (identité, clubs, records, médailles…), assemble un gros objet, l'écrit dans le fichier cache, puis le renvoie.
  6. Retour à index.php. Il reçoit le JSON, en extrait les infos et génère le HTML de la fiche (en-tête, tableaux de records, médailles…). Il génère aussi les balises SEO (voir section 16).
  7. Le navigateur affiche la page. Le HTML arrive. Le CSS l'habille, puis le JavaScript prend le relais pour les parties dynamiques : graphiques de progression (Chart.js), bouton « suivre », biographie auto-générée, carte des lieux… souvent via d'autres appels API en arrière-plan.
ℹ️ Pourquoi deux fois « id » ?
Pour les données JSON, le JS appelle directement les URLs /api/.... Pour le rendu initial côté serveur, PHP utilise apiCall() qui fait un appel HTTP interne. C'est important de le savoir car en prod (Hostinger) cet appel interne (« loopback ») se fait sans les cookies du visiteur — donc le PHP ne « voit » pas qui est connecté lors de cet appel. C'est une contrainte connue de l'hébergement.

5 · Le noyau (core/)

Le noyau regroupe le code partagé par tout le reste. Chaque page et chaque endpoint commence par inclure une partie de ces fichiers.

5.1 · core/db.php — la connexion à la base

C'est le fichier le plus important : il ouvre la connexion à MySQL et la met dans une variable appelée $conn, utilisée partout ensuite pour faire des requêtes. Il détecte aussi automatiquement si on est en local ou en prod.

// On charge d'abord les identifiants de prod (Hostinger)
require_once __DIR__ . '/credentials.php';

// Détection : sommes-nous en local (XAMPP) ou en ligne (Hostinger) ?
$isLocal = (in_array($_SERVER['SERVER_NAME'] ?? '', ['localhost','127.0.0.1'], true) || …);

// En local, si un fichier credentials_local.php existe, on prend CES identifiants
if ($isLocal && file_exists(__DIR__ . '/credentials_local.php')) {
    require __DIR__ . '/credentials_local.php';
}

// Ouverture de la connexion. $conn est LA variable utilisée partout ensuite.
$conn = new mysqli("localhost", $username, $password, $dbname);
$conn->set_charset("utf8mb4"); // supporte les accents et emojis
ℹ️ Le truc à comprendre
Dès qu'un fichier fait require core/db.php, il dispose de $conn et peut interroger la base. C'est pour ça qu'on voit partout $conn->query("SELECT …"). Les identifiants réels (mot de passe de la base) sont dans credentials.php (prod) et credentials_local.php (ton PC) — ces fichiers ne doivent jamais être partagés publiquement.

5.2 · core/auth.php — qui est connecté ?

Gère tout ce qui concerne les comptes utilisateurs. Fonctions clés :

FonctionCe qu'elle fait
generateToken()Crée un jeton aléatoire de 64 caractères (la « clé de session »).
createSession($conn,$userId)Enregistre une session en base (table user_sessions) et pose le cookie bk_token valable 30 jours.
getCurrentUser($conn)Lit le cookie bk_token, retrouve l'utilisateur en base. Renvoie ses infos ou null si non connecté.
requireAuth($conn)Force la connexion : si l'utilisateur n'est pas connecté, redirige vers login.php.
requireAuthApi($conn)Idem, mais pour l'API : renvoie une erreur JSON 401 au lieu de rediriger.
requireRole($conn,$roles)Vérifie que l'utilisateur a le bon rôle (ex. ['admin']).
logout($conn)Supprime la session en base et efface les cookies (bk_token + bk_sa_token).
🎟️ Analogie : le bracelet de festival
Quand tu te connectes, le serveur te pose un bracelet (le cookie bk_token) avec un numéro unique. À chaque page, getCurrentUser() regarde ton bracelet et vérifie dans son registre (table user_sessions) qu'il est valide et pas expiré. Pas de bracelet = visiteur anonyme.

5.3 · Les autres fichiers du noyau

  • paths.php : définit BK_BASE (le préfixe d'URL : /BK en local, vide en prod) et la fonction BK_URL(). Évite les liens cassés entre local et prod.
  • ip_logger.php : la fonction logIp() écrit chaque visite dans logs/ip_track_AAAA-MM.php. Les IP whitelistées (Google, Hostinger…) ne sont pas journalisées.
  • search_limit.php : la « source de vérité unique » des quotas de recherche (voir section 12).
  • seo.php : fabrique le titre, la description et les données structurées des profils (voir section 16).
  • insert_athle.php : insère les données scrapées dans la base (voir section 14).

6.3 · Les relations (clés étrangères) et leur comportement

ℹ️ Que se passe-t-il quand on supprime ?
  • Supprimer un athlète → ON DELETE CASCADE : toutes ses données liées (records, médailles…) sont supprimées automatiquement.
  • Supprimer un club / une épreuve / une ville → ON DELETE SET NULL : les lignes qui pointaient dessus ne sont pas supprimées, leur référence devient simplement « vide ».

7 · L'API REST (api/)

L'API est l'ensemble des « portes » qui renvoient du JSON. Chaque fichier .php du dossier api/ est une porte (un endpoint).

7.1 · Le squelette commun : api/config.php

Tous les endpoints commencent par require config.php. Ce fichier :

  1. Bloque l'accès direct (on ne peut pas ouvrir config.php seul).
  2. Pose les en-têtes JSON + CORS (autorise les appels cross-domaine).
  3. Inclut core/db.php → la connexion $conn.
  4. Inclut core/auth.php et ip_logger.php, puis appelle logIp().
  5. Définit la clé d'API BK_API_KEY et la fonction jsonResponse($data,$code) qui renvoie le JSON et ferme la connexion.

7.2 · Le pattern type d'un endpoint (à connaître par cœur)

Presque tous les endpoints suivent le même schéma — illustré ici avec search.php :

require 'config.php';                       // 1. en-têtes + $conn + auth

// 2. On lit les paramètres de l'URL (?nom=…&club=…)
$nom = trim($_GET['nom'] ?? '');

// 3. On fabrique une CLÉ DE CACHE unique = MD5 de tous les paramètres
$cacheKey  = 'search_' . md5($nom.'_'.$club.'_'. … );
$cacheFile = $cacheDir . '/' . $cacheKey . '.json';

// 4. Si une copie existe et a moins de 24 h → on la renvoie direct (CACHE HIT)
if (file_exists($cacheFile) && (time() - filemtime($cacheFile)) < 86400) {
    echo file_get_contents($cacheFile); exit;
}

// 5. CACHE MISS → on interroge la base (requêtes SQL)
$result = $conn->query("SELECT … FROM athletes WHERE …");

// 6. On assemble le résultat, on l'écrit dans le cache, et on le renvoie
@file_put_contents($cacheFile, $json, LOCK_EX);
echo $json;
✅ Pourquoi MD5 ?
Chaque combinaison de paramètres doit avoir son propre fichier cache. md5(...) transforme une longue liste de paramètres en une empreinte courte et unique (ex. search_a1b2c3…). Deux recherches identiques → même empreinte → même fichier → réponse instantanée la seconde fois.

8b · Inodes & nettoyage automatique (important pour Hostinger)

Qu'est-ce qu'un « inode » ?

🗂️ Analogie : les fiches d'un fichier cartonné
Sur un serveur, chaque fichier et chaque dossier consomme 1 « inode » (une entrée dans l'index du disque), indépendamment de sa taille. Un hébergement mutualisé comme Hostinger limite le nombre total d'inodes (souvent 200 000 à 400 000). Même si tes fichiers sont minuscules, trop de fichiers = serveur bloqué.

Le problème rencontré

Le dossier cache/ grossit sans limite : chaque recherche ou profil unique crée un fichier .json permanent. Le TTL de 24 h ne supprime rien — il marque juste le fichier comme « périmé » et il ne sera réécrit que si la même requête revient. Résultat constaté en prod : 337 000 fichiers dans cache/ (≈ 337 000 inodes, ~4,75 Go).

La solution : admin/cache_janitor.php

Un « nettoyeur » conçu pour ne pas impacter les performances :

  • Lancé uniquement par le cron (tâche planifiée), jamais pendant une visite.
  • Parcourt le dossier en streaming (opendir/readdir) → mémoire constante même sur 300 000 fichiers (pas de glob qui chargerait tout d'un coup).
  • Borné dans le temps (max_seconds) : s'arrête proprement et reprend au passage suivant si le dossier est énorme.
  • Supprime seulement les fichiers plus vieux que le TTL → ne touche jamais un cache encore servi.
# Tâche cron Hostinger (1× par jour, ex. 3 h du matin) :
curl -s "https://bokonzi.com/admin/cache_janitor.php?bk_key=…&max_seconds=25" >/dev/null 2>&1

# Test à blanc (ne supprime rien, compte seulement) :
…/cache_janitor.php?bk_key=…&dry=1

Il existe un jumeau admin/src_janitor.php pour le dossier src/ (fichiers {id}.php du scraping). src/ n'est qu'une optimisation SEO : seoFromSrcFile() retombe sur l'API si le fichier manque, donc on peut le purger sans rien casser.

✅ Résultat
Après nettoyage : ~316 000 inodes libérés (de ~339 000 à ~1 500). Le cron quotidien empêche la situation de revenir.

9.3 · La fonction apiCall()

Côté PHP, apiCall($url) fait un appel HTTP interne à l'API et décode le JSON. C'est le pont entre la couche affichage et la couche données lors du rendu initial (le premier chargement de la page). Ensuite, le JavaScript prend le relais avec fetch() pour les parties dynamiques.

⚠️ Panneaux club/épreuve = pas des pages
Les panneaux de détail (club, épreuve) ne sont pas des pages séparées : ce sont des overlays (fenêtres superposées) remplis par du JavaScript via fetch(). À l'inverse, la page Villes est rendue entièrement côté serveur (PHP). Ne cherche pas un fichier club.php : tout est dans index.php + JS.

Tous les tableaux bk-table doivent suivre cette structure en 3 tables empilées : un en-tête, les données, puis à nouveau l'en-tête. Cela donne des en-têtes « collants » en haut et en bas lors du défilement.

  <table class="bk-table"><tr><th>Col1</th><th>Col2</th></tr></table>  <!-- en-tête -->
</div>

10.2 · Composants JavaScript réutilisables

  • Panneau club : présent sur 3 pages avec un suffixe (''=Recherche, 'Accueil'=Accueil). Fonctions _openClubPanel(), _fillClubPanel(), 5 onglets.
  • Panneau épreuve : openEpreuveDetail(), 4 onglets.
  • Biographie athlète : buildAthleteBio() (~500 lignes) génère une bio automatique filtrable par années.
  • Graphiques : Chart.js 4.4.7. Le rendu se fait après l'insertion du HTML (post-render).

10.3 · Quelques pièges frontend

⚠️ À garder en tête
  • Les noms de club venant de l'API peuvent contenir un * en suffixe → utiliser rtrim($club, '* ') dans les liens.
  • Les clubs de plus de 5000 athlètes sont exclus des résultats de recherche (sauf si on filtre explicitement sur ce club).
  • Une performance avec performance_int = 0 ou NULL = conversion ratée → toujours filtrer > 0.
  • Beaucoup de CSS est en ligne dans index.php ; le reste est dans dashboard.css et common.css.

10.4 · Conversion des performances

La fonction performanceToInt() (dans Class/AthleteScraper.php) convertit un temps ou une distance texte en entier (centièmes / centimètres) pour pouvoir les trier. Exemple : 10''48 → 1048. Piège : un seul chiffre après '' est un dixième (10''9 = 10,9 s = 1090, pas 1009) — d'où le str_pad.

12.2 · Les deux fonctions clés

  • bkSearchLimit($conn, $consume) : vérifie le quota. Si $consume = true, compte cette recherche. Renvoie un tableau { blocked, reason, used, limit, remaining, … }.
  • bkSlFields($sl) : formate les champs standard à renvoyer dans les réponses JSON (pour le badge de quota).
ℹ️ Compteur par utilisateur, pas par IP
Le fichier compteur logs/.search_limits.php est indexé par u<id_user> et non par IP. Ainsi, deux personnes derrière le même WiFi ne se partagent pas le quota. Remise à zéro automatique au changement de date.

12.3 · Anti-scraping (navigation)

Dans index.php (lignes ~22-47), un compteur journalier par IP (logs/.page_limits.php) bloque l'anonyme au-delà de 200 pages/jour (redirection vers login.php?limit=1). Connectés et whitelist = illimité.

13 · Sécurité générale

  • Identifiants de base : dans core/credentials.php (jamais commité en clair publiquement).
  • Fichiers de logs protégés : chaque fichier JSON sensible commence par <?php die(); ?> — si quelqu'un l'ouvre par URL, PHP s'arrête immédiatement et ne montre rien.
  • Dossiers protégés par .htaccess : cache/, logs/.
  • Mots de passe : hachés avec password_hash() (bcrypt) — jamais stockés en clair.
  • Requêtes préparées : pour les données sensibles (auth), on utilise $conn->prepare() + bind_param() → protège contre l'injection SQL.
  • Clé API : bk_s3cr3t_2026_xK9mP, passée en ?bk_key= ou en-tête X-BK-KEY. Donne un accès illimité et des actions admin à distance (reset, bypass cache, janitors).
  • Fichiers dangereux supprimés : admin/drop_all.php et admin/reset.php ont été retirés (ils pouvaient effacer toute la base).
🚨 À ne jamais faire
Ne jamais exposer publiquement credentials.php, la clé API, ou les fichiers de logs/. Ne jamais désactiver les requêtes préparées sur l'authentification. Ne jamais réintroduire un script de « suppression totale » accessible par URL.

14 · Le pipeline de scraping

Le « scraping » est l'aspiration automatique des données depuis le site officiel athle.fr pour remplir la base de Bokonzi. C'est le système le plus complexe du projet.

14.1 · Le chemin d'une donnée

athle.fr (pages HTML) │ scrapeParallel() — télécharge 7 athlètes × 3 pages en parallèle (curl_multi) ▼ Class/AthleteScraper.php — PARSE le HTML → données structurées │ (extractIdentite, extractRecords, extractMedailles, extractProgressions…) ▼ core/insert_athle.php — insertAthleteData() → écrit en base (9 tables enfants) │ + écrit une copie JSON dans src/{id}.php ▼ MySQL (base de données Bokonzi)

14.2 · Les acteurs

FichierRôle
scraping/scraper.phpL'orchestrateur principal. Bouton DÉMARRER/ARRÊTER (fichier flag), traite par lots de 7, ignore les athlètes déjà en base, s'auto-rafraîchit toutes les 25 s. ~3,5 jours pour 300k athlètes.
scraping/scrape_functions.phpscrapeParallel() : télécharge en parallèle (curl_multi) les pages bilans / records / sélections.
Class/AthleteScraper.phpLe parseur : transforme le HTML brut d'athle.fr en données propres. Contient performanceToInt().
core/insert_athle.phpinsertAthleteData() : insère tout en base. Utilise un cache mémoire des référentiels pour éviter les requêtes répétées. Si l'athlète existe déjà → on supprime ses enfants (CASCADE) et on réinsère tout.
scraping_v2/Pipeline v2 (orienté objet) : découverte des classements → table nom_et_liens, puis scraping par année / par épreuve. Inclut des outils de drill-down et de nettoyage de doublons.

14.3 · Fichiers de progression (pour reprendre après interruption)

Le scraping peut tourner des jours. Pour reprendre où il s'était arrêté, il écrit son avancement dans des fichiers : progress.txt (ID courant), urls_cache.json (cache des URLs), failed.json (athlètes en échec). La table athlete_scrape_log permet d'éviter de re-scraper un athlète vu il y a moins de 24 h.

ℹ️ Suivi à distance
admin/remote_check.php?bk_key=…&action=scrape_status donne l'état des pipelines (total en base, restants, %, derniers athlètes, audit qualité) au format JSON.

16 · SEO (référencement)

Le SEO, c'est ce qui aide Google à comprendre et bien classer les pages. Bokonzi le fait sérieusement car son trafic dépend du référencement.

  • Open Graph & Twitter Cards : aperçu riche quand on partage un lien sur les réseaux.

  • sitemap.php : génère dynamiquement le plan du site (toutes les pages + clubs + épreuves + villes + athlètes paginés).
  • noindex sur les pages comparer, tuto, et profils 404.

17.3 · Contraintes Hostinger à connaître

⚠️ Particularités de l'hébergement mutualisé
  • Limite d'inodes : nombre total de fichiers limité → d'où le cache janitor (section 8b).
  • Appels « loopback » sans cookies : quand le PHP s'appelle lui-même (apiCall vers sa propre API), les cookies du visiteur ne sont pas transmis.
  • Certains en-têtes HTTP sont bloqués par l'hébergeur.
  • MySQL non optimisé : certaines requêtes lourdes (UNION, IN sur sous-requêtes) provoquent des timeouts — privilégier EXISTS et les index.

20 · Checklist : reprendre le projet de zéro

Si tu récupères ce projet sans rien connaître, voici l'ordre à suivre.

  1. Installe XAMPP et place le dossier du projet dans C:\xampp\htdocs\BK. Démarre Apache et MySQL.
  2. Crée une base locale dans phpMyAdmin (ex. bk_local), puis configure core/credentials_local.php avec tes identifiants locaux.
  3. Crée les tables en ouvrant admin/setup_bdd.php (ou admin/local_setup.php qui guide).
  4. Ouvre http://localhost/BK : le site doit s'afficher (base vide au début).
  5. Comprends le flux : relis les sections 2 (vue d'ensemble) et 3 (cycle de vie) en suivant dans le code index.php → api/athlete.php → core/db.php.
  6. Pour des données : soit tu importes une sauvegarde de la base de prod, soit tu lances le scraping (section 14) — attention, c'est long.
  7. Avant toute modif en prod : teste en local, puis uploade le fichier modifié via le file manager Hostinger. Vide le cache concerné après coup.
  8. Garde sous les yeux le fichier CLAUDE.md à la racine : c'est la référence rapide la plus détaillée (mais vérifie toujours les valeurs dans le code réel, elles peuvent avoir évolué).
✅ Le mot de la fin
Tout le projet repose sur 4 idées simples : (1) une base MySQL alimentée par le scraping, (2) une API qui lit cette base et met en cache, (3) des pages PHP/JS qui appellent l'API, (4) un noyau partagé (connexion, auth, quotas). Si tu gardes cette carte mentale, tu peux retrouver n'importe quelle fonctionnalité en partant de la couche concernée.
