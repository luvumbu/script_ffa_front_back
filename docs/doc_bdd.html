Schéma complet de la base de données

Les 29 tables MySQL, colonne par colonne, avec les relations et leur comportement de suppression
La base est définie dans core/dbCheck_athle.php (le fichier qui exécute les CREATE TABLE). Tout est en InnoDB / UTF-8 MB4 (support complet des accents et emojis). Les performances sont toujours stockées en entier (centièmes de seconde pour les courses, centimètres pour les sauts/lancers) plus une version texte « brute » pour l'affichage.

⚠️ Le double identifiant — la chose à comprendre avant tout

🚨 Chaque athlète a DEUX numéros
ColonneOrigineUsage
athlete_id_externeLe numéro venant d'athle.fr (la source)Dans les URLs du site (?id=). C'est CELUI à utiliser dans le dashboard.
id_athleteNuméro interne auto-incrémenté par MySQL (clé primaire)Pour relier les tables entre elles (toutes les clés étrangères pointent dessus).
Toutes les tables « enfants » (records, médailles…) utilisent id_athlete (interne). Mais les tables de suivi par email (athlete_follows) et les compteurs de vues utilisent athlete_id_ext (externe). Confondre les deux est l'erreur n°1 du projet.

Comportement des suppressions (très important)

🚨 Supprimer un athlète = effacer tout son palmarès
La clé étrangère id_athlete est en ON DELETE CASCADE dans toutes les tables enfants. DELETE FROM athletes WHERE id_athlete = X supprime automatiquement tous ses records, résultats, médailles, etc. C'est aussi ce qu'utilise le scraping pour mettre à jour un athlète : il supprime ses enfants puis réinsère tout.
✅ Supprimer un club/épreuve/ville = sans danger pour les perfs
Les clés étrangères vers les référentiels sont en ON DELETE SET NULL. Supprimer un club ne supprime pas les records associés : leur colonne id_club devient simplement NULL.

Pour masquer un profil sans rien supprimer, on met visible = 0 (voir la gestion des signalements dans la doc principale).
