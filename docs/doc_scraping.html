Le pipeline de scraping, pas à pas

Comment une donnée passe d'une page HTML d'athle.fr jusqu'à la base de données
Le scraping est le système le plus complexe du projet. Il télécharge les pages d'athle.fr, les parse (extrait les infos du HTML), convertit les performances en nombres, puis insère tout en base de façon optimisée. Cette page suit ce chemin de bout en bout.
Le flux complet 1 · L'orchestrateur (scraper.php) 2 · Le téléchargement parallèle 3 · Le parseur (AthleteScraper) 4 · performanceToInt() — les 7 patterns 5 · Découpage du nom & catégorie 6 · L'insertion optimisée 7 · Progressions en fichier 8 · Reprise après interruption

Le flux complet

athle.fr (3 pages HTML par athlète : bilans / records / selections) │ │ ① scrapeParallel() — curl_multi : 7 athlètes × 3 pages = 21 requêtes EN PARALLÈLE ▼ HTML brut │ │ ② AthleteScraper — parse le HTML → 9 tableaux structurés │ (identite, clubs, medailles, selections, progressions, │ records, podiums, resultats, niveaux) │ │ ③ performanceToInt() — « 10''48 » → 1048 (centièmes/cm) ▼ Données propres │ │ ④ insertAthleteData() — cache mémoire + batch INSERT (9 sections) │ si l'athlète existe : DELETE CASCADE des enfants puis réinsert ▼ MySQL + copie JSON dans src/{id}.php

Le cycle (toutes les 25 s)

  1. Charge les URLs depuis la table nom_et_liens (cache urls_cache.json).
  2. Collecte 7 athlètes non présents en base à partir de la position sauvegardée (progress.txt).
  3. scrapeParallel() télécharge leurs 21 pages.
  4. Pour chacun : parse → JSON src/{id}.php → insertAthleteData().
  5. Sauvegarde la position dans progress.txt, échecs dans failed.json.
  6. sleep(1) (throttle athle.fr) puis recharge.

2 · Le téléchargement parallèle — scrapeParallel()

Dans scraping/scrape_functions.php. Signature : scrapeParallel(array $athleteIds, string $baseUrl = "https://athle.fr/athletes/").

  • Crée un handle curl_multi pour chaque combinaison athlète × section (bilans / records / selections).
  • Total = N × 3 requêtes lancées simultanément. Timeout 15 s par requête.
  • Attend que tout soit fini, ne garde que les réponses HTTP 200.
// Structure de retour
[
  548525 => [ 'bilans' => html|null, 'records' => html|null, 'selections' => html|null ],
  2643370 => [ ... ],
]
✅ Pourquoi parallèle ?
Télécharger 21 pages une par une prendrait ~21 × le temps réseau. En parallèle, on attend seulement la plus lente. Gain : ~3,5 jours pour 300k athlètes au lieu de ~17 jours en séquentiel.

3 · Le parseur — Class/AthleteScraper.php

Une classe qui prend l'HTML brut et en extrait 9 tableaux. scrapeAll() orchestre l'extraction.

MéthodeCe qu'elle extrait

extractProgressions()Meilleures perfs par saison (section_4). Détecte l'épreuve courante, l'année, extrait le vent, appelle performanceToInt() et getCategorieCode()

extractResultats()section_3 : tous les résultats de l'année avec date complète
extractSelections()Sélections équipe de France (header + résultat appariés)
extractNiveaux()section_9 : N2 (28 pts) → code + points + perfs justificatives

4 · performanceToInt() — les 7 patterns (à comprendre absolument)

Fonction statique (lignes ~1014-1060) qui convertit une performance texte en entier : centièmes de seconde pour les courses, centimètres pour les sauts/lancers. Les 7 patterns sont testés dans cet ordre :

#FormatExempleRésultat
1Xh Y'ZZ''CC (heures)1h23'45''12((1×3600+23×60+45)×100)+12
2X'YY''CC (min+centièmes)3'43''65((3×60+43)×100)+65 = 22365
3X'YY (min sans centièmes)12'09(12×60+9)×100 = 72900
4XX''CC (sec+centièmes)10''4810×100+48 = 1048
5XmYY (distance, m)6m306×100+30 = 630
6X.YY (distance décimale)7.347×100+34 = 734
7XXXX (entier seul)734734×100 (fallback)
🚨 Le piège du dixième (str_pad)
Quand il n'y a qu'un seul chiffre après '', m ou ., c'est un dixième, pas un centième. Le code fait str_pad($chiffre, 2, '0', STR_PAD_RIGHT) → ajoute un zéro à droite :
BrutSANS padding (BUG)AVEC padding (CORRECT)
10''91009 (10,09 s) ❌1090 (10,9 s) ✅
1'53''311303 ❌11330 ✅
6m3603 (6,03 m) ❌630 (6,30 m) ✅
Un script de correction existe : admin/fix_perf_int.php (?go pour exécuter).

5 · Découpage du nom & catégorie

splitNomPrenom() (lignes ~941-978)

Sépare nom de famille et prénoms par heuristique de majuscules : les mots tout en majuscules (longueur > 1) = nom de famille (peut être multi-mots : « VAN DER ZYPPE »), le reste = prénoms. Fonctionne dans les deux sens : « VAN DER ZYPPE Antonine » ou « Ndenga LUVUMBU ».

getCategorieCode($anneeNaissance, $anneeSaison) (lignes ~986-1004)

Calcule l'âge (saison − naissance, approximation sans jour/mois) et renvoie le code FFA : ≤7 EA, ≤9 PO, ≤11 BE, ≤13 MI, ≤15 CA, ≤17 JU, ≤22 ES, ≤39 SE, ≤49 V1, ≤59 V2, ≤69 V3, sinon V4.

6 · L'insertion optimisée — core/insert_athle.php

loadRefCache($conn)

Charge les 6 tables de référence (villes, clubs, épreuves, compétitions, catégories, nationalités) en mémoire sous forme [table][valeur] = id. Fait une fois au démarrage.

cachedGetOrInsertId(&$cache, $conn, …)

Pour obtenir l'id d'un club/épreuve/ville : (1) regarde le cache mémoire (0 requête si trouvé), (2) sinon INSERT IGNORE, (3) si déjà existant, SELECT pour récupérer l'id. Élimine ~95 % des SELECT.

insertAthleteData($scraper, $conn, &$cache) — les 9 sections

  1. Identité : si l'athlète existe déjà → UPDATE + DELETE CASCADE de ses 8 tables enfants ; sinon INSERT.
  2. à
  3. Clubs, médailles, sélections, progressions, records, podiums, résultats : un batch INSERT par section (1 requête pour N lignes).
  4. Niveaux + perfs : séquentiel (chaque niveau génère un id dont dépendent ses perfs).
✅ Le gain
Pour un athlète typique : ~9-15 requêtes SQL au lieu de 200+. Stratégie « DELETE + réinsert » plutôt que « UPDATE des enfants » (plus simple et fiable).

Index256 shards archives/.prog_idx/<0-255>.json (par id_athlete & 0xFF)
Helpercore/progressions_store.php : progStoreAppendBatch(), progStoreLoadForAthlete()
Lectureapi/athlete.php lit le fichier si activé, sinon le SQL classique

Lors de l'insertion, le code écrit puis relit immédiatement pour vérifier l'intégrité ; en cas d'écart, il log dans archives/.prog_idx/_errors.log.
