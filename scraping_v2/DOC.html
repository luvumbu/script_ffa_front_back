Prologue

Ce que vous devez savoir avant tout

Si vous decouvrez ce projet aujourd'hui, lisez ces quelques pages avant tout le reste. Elles posent le vocabulaire et les enjeux.
La maison Bokonzi tient une base de donnees consacree a l'athletisme francais. Chaque athlete, chaque club, chaque epreuve, chaque record y a sa place. Mais d'ou viennent ces donnees ? D'un site officiel, athle.fr, geree par la Federation Francaise d'Athletisme, qui publie en libre acces les classements de toutes les competitions. La difficulte : ce site n'offre pas de fichier telechargeable de tout son contenu. Il faut le parcourir page apres page, en programmant un robot qui lit le HTML et en extrait ce qui interesse. Cette technique s'appelle le scraping. scraping_v2 est la deuxieme generation de ce robot, plus intelligente et plus controlable que la premiere.

Le scraping en deux phrases. Un programme qui se fait passer pour un navigateur web, telecharge des pages HTML d'un site internet, puis extrait des informations precises (noms, dates, scores) en analysant le code source de ces pages. C'est legal tant qu'on respecte le rythme du serveur et qu'on n'extrait que des donnees publiques.

Pourquoi pas une API ? Une API serait une porte officielle : on lui demande "donne-moi tous les athletes de Lyon", elle repond en JSON propre. Mais athle.fr n'en propose pas. Il faut donc passer par la porte de service : telecharger les pages HTML que les humains voient, et faire le travail d'extraction nous-memes.

Le projet en trois etages

Pour comprendre la place de scraping_v2, il faut visualiser le projet Bokonzi comme trois etages superposes :

ETAGE 3 ┃ Le site bokonzi.com (PHP + MySQL + JS) ┃ L'utilisateur final consulte les athletes, clubs, records. ─────────┃──────────────────────────────────────────────────────────── ETAGE 2 ┃ La base MySQL ┃ Tables : athletes, clubs, epreuves, records, ... (23 tables) ─────────┃──────────────────────────────────────────────────────────── ETAGE 1 ┃ Le pipeline d'acquisition ← C'EST ICI QU'ON SE TROUVE ┃ Scraping athle.fr → JSON → import → MySQL

L'etage 1 lui-meme se decompose en deux pipelines historiques :

Comprendre l'enchainement.

1. Sur athle.fr, il existe des pages de classements du type "les 500 meilleures performeuses du 800m en 2024". Chacune contient les liens vers les fiches des athletes classees.

2. scraping_v2 parcourt ces pages de classements et stocke les liens individuels dans la table nom_et_liens.

3. scraping/ (l'ancien pipeline) lit ensuite nom_et_liens et va scraper chaque fiche individuelle pour en extraire le palmares complet.

Sans scraping_v2, on ne sait pas quels athletes scraper. Sans scraping/, on n'a que des URLs sans contenu.

Le piege qui a hante la premiere version. Toutes ces tables soeurs partagent exactement le meme prefixe pour leurs colonnes : u489596434_bokonzi_on_id, u489596434_bokonzi_on_url, etc. Le nom de la table n'apparait jamais dans le nom de colonne. Si vous touchez au code, ne supposez pas que la colonne s'appelle sprint_piste_h_id — cela provoquerait une page blanche immediate.

Le but final de scraping_v2 en une page

  1. Lire ces quatorze tables et comprendre les URLs qu'elles contiennent.
  2. Laisser l'operateur cocher les annees a conserver (les 22 annees disponibles, de 2004 a 2026, ne sont pas toutes utiles).
  3. Pour chaque URL retenue, parcourir chaque page du classement (1 a 80 pages).
  4. Sur chaque page, extraire la liste des athletes presents et leur URL de fiche.
  5. Inserer ces URLs dans nom_et_liens pour que l'ancien pipeline les scrape ensuite.

Ordre de grandeur. Une seule table source contient typiquement 100 a 300 lignes. Chaque ligne pointe vers un classement de 1 a 80 pages. Chaque page liste jusqu'a 50 athletes. Au total, un cycle complet de scraping_v2 peut decouvrir plusieurs centaines de milliers d'athletes en quelques heures — sans saturer athle.fr grace a un delai de 300 millisecondes entre chaque telechargement.

Decision de design : pourquoi cette decomposition ?

Le principe directeur du projet est qu'une classe egale une responsabilite. Si demain on decide de scraper un autre site que athle.fr, seul PageAnalyzer sera a reecrire. Si on veut decoder des URLs differentes, seul UrlAnalyzer change. Cette modularite paie un cout — cinq fichiers a maintenir au lieu d'un — mais offre un benefice considerable : on peut tester chaque piece isolement (cf. test_page.php), comprendre le code sans charger toute l'architecture en tete, et remplacer une piece sans casser les autres.

Couplage faible, cohesion forte. C'est le mantra. Chaque classe doit dependre du minimum d'autres classes (couplage faible), mais doit etre tres cohesive en interne (cohesion forte) — toutes ses methodes parlent du meme sujet. UrlAnalyzer ne fait que decoder des URLs. PageAnalyzer ne fait que telecharger et parser. Aucune ne sait que l'autre existe.

Les fichiers d'etat — la memoire du systeme

Le dossier state/ est cree automatiquement la premiere fois que le runner demarre. Il contient deux types de fichiers :

  • Des flags (extensions .flag) : leur simple presence indique qu'une operation est en cours. Suppression = arret.
  • Des fichiers d'etat (extensions .json) : ils gardent en memoire l'avancement et les statistiques. Lisibles a l'oeil nu.

Pourquoi pas une table MySQL ? Question legitime. Mais les fichiers ont trois avantages : (1) ils sont consultables instantanement sans requete SQL ; (2) ils survivent meme si la BDD est temporairement coupee ; (3) on peut les editer a la main en cas d'anomalie. Pour l'etat d'un processus, le fichier reste souvent plus pragmatique que la BDD.

Chapitre II

L'antichambreindex.php

Tout commence ici. Une page qui parle a la fois a celui qui configure et a celui qui supervise — l'unique point d'entree du systeme.
index.php est l'unique porte d'entree. Quand vous tapez l'URL localhost/BK/scraping_v2/ ou bokonzi.com/scraping_v2/, c'est ce fichier que le serveur execute. Il fait quelque cinq cents lignes, dont la moitie en PHP pur (chargement des classes, traitement des formulaires, calculs) et l'autre moitie en HTML (formulaires, tableaux d'analyse, bouton de demarrage). La logique est lineaire : on charge les prerequis, on instancie les classes, on traite les soumissions de formulaire, on lance un cycle de scraping si l'on est en cours d'execution, puis on rend la page. Le secret tient dans une variable simple : la presence ou l'absence du fichier state/scraper_v2_running.flag, qui transforme la meme page de configuration en cockpit de supervision.

Comment marche une page PHP ? Quand le navigateur demande /scraping_v2/, Apache lit le fichier index.php du dossier, fait tourner le code PHP de haut en bas, et envoie le resultat (du HTML) au navigateur. Chaque rechargement de page = nouvelle execution complete du code. Il n'y a pas de "memoire" entre deux chargements — tout ce qu'on veut conserver doit etre ecrit en BDD ou dans un fichier.

array_flip() : echange les cles et les valeurs d'un tableau. [2024, 2025] devient [2024 => 0, 2025 => 1]. Pourquoi ? Sur un seul check c'est anecdotique, mais dans une boucle qui passe des milliers de fois, ca devient determinant.

L'auto-refresh progressif — ligne 142 a 159

Quand un scraping est en cours, la page se recharge automatiquement pour declencher le prochain cycle. Mais le delai s'adapte aux conditions :

// Lecture des compteurs actuels
$pages = (int)($runnerProgress['stats']['pages_traitees'] ?? 0);
$errs  = (int)($runnerProgress['stats']['fetch_errors'] ?? 0);

// 5 paliers selon la sante du scraping
if ($errs > 0 && $errs >= $pages * 0.3) {
    $refresh = 15;     // >30% erreurs : on ralentit serieusement
} elseif ($pages < 5) {
    $refresh = 10;     // debut : on demarre doucement
} elseif ($pages < 20) {
    $refresh = 7;
} elseif ($pages < 50) {
    $refresh = 5;
} else {
    $refresh = 3;      // vitesse de croisiere
}

// Envoi du header HTTP au navigateur
// "Refresh: 5" = recharger la page dans 5 secondes
header("Refresh: $refresh");

Pourquoi cette progressivite ? Hostinger surveille les requetes HTTP entrantes. S'il en voit beaucoup en peu de temps depuis la meme IP, il peut declencher une protection anti-DDoS et bloquer l'IP. Demarrer a 10 secondes et accelerer progressivement evite ce reflexe, tout en gardant une vitesse confortable une fois etabli un rythme de croisiere stable.

Le pattern Post / Redirect / Get

Quand l'utilisateur clique le bouton DEMARRER, le navigateur envoie une requete POST. Si index.php traitait directement le POST et rendait la page, un simple F5 du navigateur re-soumettrait le formulaire — et lancerait un nouveau scraping. Pour eviter cela, le pattern PRG est applique :

1. Navigateur --[POST action=start]--> index.php 2. index.php --[traite le POST, lance le runner]--> state/ 3. index.php --[HTTP 302 Location: ?table=...]--> Navigateur 4. Navigateur --[GET avec les params]--> index.php 5. index.php --[lit l'etat, rend la page]--> Navigateur

Si l'utilisateur fait F5 a l'etape 5, c'est juste un GET qui se reproduit — pas de re-soumission, pas de relance accidentelle.

Cas d'erreur possibles

Fichier prerequis manquant. Page d'erreur explicite listant ce qui manque. Cause typique : upload partiel sur Hostinger. Solution : verifier le File Manager Hostinger et reuploader les fichiers manquants.
Connexion BDD impossible. Erreur PHP fatale sur le require_once 'core/db.php'. Le fichier de credentials BDD est mal configure. Solution : verifier core/credentials.php et tester avec diagnose.php.
Aucune table source detectee. Le tableau $tables est vide, l'interface affiche un encart rouge. Cause : le prefixe de tables a change, ou les tables ont ete supprimees. Solution : verifier en BDD avec SHOW TABLES LIKE 'u489596434_bokonzi_on_%'.
Flag present mais cache candidates introuvable. Scenario anormal apres un nettoyage partiel du dossier state. Solution : POST action=reset via le bouton "Effacer la progression".
Chapitre III

Le miroirjarvis.php

Un tableau de bord pur observateur — il ne touche rien, il regarde. Et il le fait avec un esthetisme assume.
Il y a deux manieres de superviser une operation longue. La premiere est dense : tout dans une page, configuration et execution. C'est index.php. La seconde est contemplative : la meme information distillee en quatre compteurs et un graphique circulaire, sur fond noir, avec une horloge qui bat en temps reel. C'est jarvis.php. Inspire des HUD de films de science-fiction, ce fichier ne contient aucun bouton d'action — il observe et rapporte. L'idee : l'ouvrir dans un onglet pendant qu'on travaille ailleurs, et lever de temps en temps les yeux vers le pourcentage d'avancement. Aucune classe lib n'est chargee, seule la connexion BDD et la lecture des fichiers d'etat suffisent.

Pourquoi un fichier separe ? Parce que index.php est deja dense — il configure ET supervise. Avoir une page dediee a la supervision seule permet de l'afficher en plein ecran, ou sur un second moniteur, sans encombrer l'interface principale. C'est un principe d'UX : une intention par ecran.

Chapitre VI

Le menagecleanup_duplicates.php

Le pendant indispensable d'un pipeline qui insere sans contrainte. Quand les doublons s'accumulent, ce fichier les efface par fournees de cinq cents.
La philosophie du pipeline scraping_v2 est claire : ne jamais bloquer l'INSERT pour cause de doublon. Cela permet a la production d'aller vite, et reporte le menage a plus tard. cleanup_duplicates.php est ce plus tard. Le fichier identifie les paires de lignes partageant la meme URL et supprime celle qui possede l'identifiant le plus eleve — preservant ainsi la plus ancienne. Le travail s'effectue par lots de cinq cents lignes pour ne jamais frapper le mur du timeout Hostinger, avec auto-rafraichissement toutes les deux secondes tant qu'il reste du grain a moudre. Le fichier propose aussi de creer un INDEX sur la colonne url, ce qui accelere le DELETE d'un facteur cent — etape facultative mais fortement recommandee avant un cleanup massif.

Qu'est-ce qu'un doublon dans nom_et_liens ? Deux lignes avec la meme URL. Si le scraper passe deux fois sur la meme page (par exemple a la suite d'un redemarrage), chaque athlete est insere deux fois. Pas de probleme fonctionnel — mais avec le temps, la table grossit pour rien.

Pourquoi ne pas ajouter une contrainte UNIQUE ? Bonne question. Reponse : parce que cela ferait echouer l'INSERT au moindre doublon, et donc rendrait le pipeline fragile. On prefere accepter l'INSERT toujours, et faire le menage a part. Cette decision se paie en place disque, mais s'achete en simplicite de code.

Decision de design — pourquoi un index de prefix 191 ?

Lors de l'ajout de l'INDEX, on ne couvre que les 191 premiers caracteres :

ALTER TABLE nom_et_liens ADD INDEX idx_url (url(191))

Calcul : la limite InnoDB pour une cle d'index est de 767 octets en row format Antelope/Compact (le defaut sur de nombreux serveurs MySQL d'hebergement mutualise). En utf8mb4 (chaque caractere fait 4 octets), on a donc :

767 octets / 4 octets par caractere = 191 caracteres maximum

Couvrir plus declencherait l'erreur Specified key was too long; max key length is 767 bytes. Sur 191 caracteres, l'index est tout a fait efficace (une URL d'athle.fr a typiquement 150-300 caracteres, donc les premiers 191 suffisent largement a discriminer).

public function analyze($url) {
    // parse_url decoupe l'URL en hote, chemin, query, etc.
    $parts = parse_url($url);

    // Si URL malformee ou sans parametres : echec
    if (!$parts || empty($parts['query'])) {
        return [
            'valide'    => false,
            'erreur'    => 'URL invalide ou sans query string',
            'url_brute' => $url,
        ];
    }

    // parse_str transforme "a=1&b=2" en ['a'=>'1', 'b'=>'2']
    // par reference dans $params
    parse_str($parts['query'], $params);

    // Construction du tableau de retour
    $analysis = [
        'valide'           => true,
        'url_brute'        => $url,
        'hote'             => $parts['host'] ?? null,
        'chemin'           => $parts['path'] ?? null,
        'parametres_bruts' => $params,

        // Champs decodes via le JSON dictionnaire
        'type_page'        => $this->decodeBase($params['frmbase'] ?? null),
        'annee'            => isset($params['frmannee'])
                              ? (int)$params['frmannee'] : null,
        'epreuve_code'     => $params['frmepreuve'] ?? null,
        'epreuve_libelle'  => null,  // rempli plus tard par EpreuveMapper
        'sexe'             => $this->decodeSexe($params['frmsexe'] ?? null),
        'categorie'        => $this->decodeCategorie($params['frmcategorie'] ?? null),

        // Fallback "(toutes)" si parametre vide
        'departement'      => empty($params['frmdepartement'])
                              ? '(toute la France)'
                              : $params['frmdepartement'],
        'ligue'            => empty($params['frmligue'])
                              ? '(toutes ligues)'
                              : $params['frmligue'],
        'nationalite'      => empty($params['frmnationalite'])
                              ? '(toutes)'
                              : $params['frmnationalite'],

        // Pagination : position est l'offset, page = position/50 + 1
        'pagination'       => [
            'position'     => isset($params['frmposition'])
                                ? (int)$params['frmposition'] : 0,
            'page_estimee' => isset($params['frmposition'])
                                ? floor((int)$params['frmposition'] / 50) + 1
                                : 1,
            'taille_page'  => 50,
        ],
        'alertes'          => [],
    ];

    // Verifications de coherence -> remplissent les alertes
    if (empty($analysis['annee']))         $analysis['alertes'][] = "Aucune annee...";

    if (empty($params['frmsexe']))         $analysis['alertes'][] = "Aucun sexe...";

}

Chapitre VIII

L'apprentilib/EpreuveMapper.php

Personne n'a la liste officielle des codes FFA. Cette classe l'apprend, en croisant deux colonnes que la BDD contient deja.
Le probleme est elegant. Les URLs d'athle.fr utilisent un code numerique pour designer une epreuve : frmepreuve=208. Mais ce code, en lui-meme, ne dit rien — il faudrait connaitre la table de correspondance pour savoir que 208 designe le 800 metres. Aucune liste publique n'existe. EpreuveMapper resout cela par un detour eclatant : les tables sources contiennent deja en parallele l'URL et le libelle ("2004 | 800m | F"). Il suffit donc de croiser les deux pour apprendre, automatiquement, que 208 → "800m". Le cache se construit a la volee a chaque chargement de page, et s'enrichit lorsque de nouvelles tables sont ajoutees. C'est de l'intelligence artificielle au sens le plus modeste du terme : un programme qui apprend a partir de donnees existantes.

Le principe en image. Imaginez une bibliotheque ou chaque livre porte deux etiquettes : une cote numerique (208) et un titre humain (800m). On voit beaucoup de livres avec la cote 208 portant le titre "800m" — on en deduit que 208 = 800m. Apres mille livres, on a appris toute la classification. EpreuveMapper fait exactement ca, mais en quelques millisecondes, en parcourant les colonnes url et epreuve des quatorze tables sources.

public function chargerDepuisTables(array $tables) {
    // Construit les noms de colonnes complets
    $colUrl = $this->prefixe . '_url';       // u489...on_url
    $colEpr = $this->prefixe . '_epreuve';   // u489...on_epreuve

    foreach ($tables as $table) {
        // Securite : on ne garde que [a-zA-Z0-9_] pour empecher injection SQL
        // avant interpolation dans la requete
        $tableSafe = preg_replace('/[^a-zA-Z0-9_]/', '', $table);

        // Verifier que la colonne url existe dans cette table
        // (toutes les tables ne sont pas toujours bien formees)
        $check = $this->conn->query("SHOW COLUMNS FROM `$tableSafe` LIKE '$colUrl'");
        if (!$check || $check->num_rows === 0) continue;

        // SELECT toutes les paires (url, epreuve) de la table
        $r = $this->conn->query(
            "SELECT `$colUrl` AS url, `$colEpr` AS epr FROM `$tableSafe`"
        );
        if (!$r) continue;

        // Pour chaque ligne, on apprend une paire (code, libelle)
        while ($row = $r->fetch_assoc()) {
            $code    = $this->extraireCode($row['url']);
            $libelle = $this->extraireLibelle($row['epr']);

            // On ignore si l'un des deux manque
            if ($code !== null && $libelle !== null) {
                // Si premiere fois : on cree l'entree
                if (!isset($this->cache[$code])) {
                    $this->cache[$code] = [
                        'libelle'     => $libelle,
                        'tables'      => [$tableSafe],
                        'occurrences' => 1,
                    ];
                } else {
                    // Sinon on incremente le compteur
                    $this->cache[$code]['occurrences']++;

                    // Et on note la table si pas deja vue
                    if (!in_array($tableSafe, $this->cache[$code]['tables'])) {
                        $this->cache[$code]['tables'][] = $tableSafe;
                    }
                }
            }
        }
    }

    // Tri numerique des codes pour affichage ordonne
    ksort($this->cache, SORT_NUMERIC);
    $this->cacheChargee = true;
}

private function extraireCode($url) {
    $parts = parse_url($url);
    if (empty($parts['query'])) return null;
    parse_str($parts['query'], $params);
    // On extrait frmepreuve du tableau de parametres
    return $params['frmepreuve'] ?? null;
}

private function extraireLibelle($epreuveColonne) {
    // Format attendu : "ANNEE | LIBELLE | SEXE"
    // explode coupe sur |, array_map(trim) nettoie les espaces
    $parts = array_map('trim', explode('|', $epreuveColonne));

    // On prend le morceau du milieu (index 1) si format conforme
    if (count($parts) >= 2) return $parts[1];
    return null;
}

Decision de design — apprentissage dynamique vs liste statique

Une alternative aurait ete de coder en dur la liste des codes FFA dans un fichier (200 = 100m, 208 = 800m, etc.). Pourquoi ne pas l'avoir fait ?

  1. Pas de liste officielle. Athle.fr ne publie pas cette table de correspondance. Il faudrait la construire manuellement, et la maintenir a la main.
  2. Robustesse. Si athle.fr ajoute une nouvelle epreuve (par exemple le 60m haies), notre liste statique sera obsolete sans le savoir. L'apprentissage dynamique decouvre automatiquement les nouveaux codes des qu'ils apparaissent en BDD.
  3. Verification croisee. Le mapping ne marche que si la BDD est coherente. Si frmepreuve=208 donne tantot "800m" tantot "1500m", on a un probleme — l'apprentissage dynamique le rend visible (le compteur d'occurrences signale les conflits).
Cout en performance. Cette classe lit l'ensemble des quatorze tables a chaque chargement de page d'index.php. Sur des tables de plusieurs milliers de lignes, cela peut prendre une demi-seconde. L'EXPLICATION.txt prevoit un cache sur disque de 24 heures pour plus tard. Pour l'instant, le cout reste tolerable.
Tri final. Apres ingestion, ksort($this->cache, SORT_NUMERIC) trie le cache par codes numeriques croissants. Cela garantit un affichage ordonne (200, 208, 209, ...) dans le tableau de mapping de l'interface.

Table sans colonne url. Le SHOW COLUMNS defensif evite l'erreur SQL. La table est simplement sautee.

private function extraireMeta($nomTable) {
    // Retirer le prefixe : u489596434_bokonzi_on_sprint_piste_h -> sprint_piste_h

Decision de design — pourquoi un prefixe fixe partout ?

L'erreur initiale a coute une page blanche : on a suppose que la colonne id de la table sprint_piste_h s'appellerait sprint_piste_h_id. C'etait faux. Le prefixe u489596434_bokonzi_on_ a ete utilise lors de l'import initial pour toutes les colonnes de toutes les tables, independamment de leur nom. Pourquoi un tel choix ?

  1. Coherence d'import. Probable trace d'un outil de migration qui prefixait tout par le nom de la BDD source.
  2. Eviter les collisions. Si on faisait des UNION entre tables, des noms de colonnes identiques entre tables differentes (ex: id) ne posent pas probleme s'ils sont prefixes.
  3. Trace historique. Cela vient probablement d'un export Hostinger en CSV qui prefixe automatiquement les colonnes par le nom de la base. Le code l'accepte comme une donnee de la realite.
Le piege a ne pas oublier. Quand on ajoute une methode a cette classe, toujours partir de $this->prefixe et JAMAIS du nom de la table. Le test : si la methode fonctionne sur sprint_piste_h mais casse sur demi_fond_piste_f, c'est qu'on a infere le nom de colonne depuis le nom de table.

Securite SQL

Toutes les methodes appliquent preg_replace('/[^a-zA-Z0-9_]/', '', $table) avant interpolation. Pourquoi ? Parce que le nom de table provient potentiellement de $_GET['table'] — donc d'un attaquant. Si on interpolait directement, un parametre malicieux comme ?table=foo; DROP TABLE users; pourrait executer du SQL non desire (injection SQL).

Injection SQL : technique d'attaque consistant a inserer du code SQL dans une valeur d'entree pour modifier la requete executee. La meilleure defense est l'utilisation de prepared statements (avec ? et bind_param). Pour les noms de table qui ne peuvent pas etre parametrise, on filtre les caracteres autorises — ici uniquement a-zA-Z0-9_.

Cas d'erreur possibles

Table inexistante. SELECT COUNT(*) FROM `inexistante` retourne false, la methode retourne 0. Pas de crash mais resultat trompeur. Toujours verifier que la table est dans la liste de listerTables() avant interrogation.
Format epreuve non standard. Si la colonne contient autre chose que "ANNEE | LIBELLE | SEXE", SUBSTRING_INDEX retourne quand meme une chaine (potentiellement vide), qui castee en int donne 0. Les annees inhabituelles apparaissent groupees sous "0" dans le resultat.
Prefixe modifie. Si la BDD est migree sur un autre Hostinger avec un autre nom (par exemple u100123456_), il faut adapter la valeur par defaut du constructeur. Sinon listerTables() retournera zero table.

Qu'est-ce que curl ? Un outil qui telecharge des donnees depuis une URL. La librairie php-curl permet d'envoyer une requete HTTP exactement comme le ferait un navigateur, et de recuperer la reponse. On peut definir des options : temps maximum d'attente, suivre les redirections automatiquement, accepter gzip, se faire passer pour Chrome 120, etc.

Qu'est-ce qu'une regex ? Une expression reguliere est un motif qui decrit une famille de chaines de caracteres. Par exemple, /\d{4}/ reconnait 4 chiffres consecutifs. On les utilise pour extraire des morceaux precis d'un texte. Ici, on cherche dans le HTML les balises <tr> qui contiennent un lien /athletes/123/.

    $ch = curl_init();

    // Configuration de la requete (toutes les options en bloc)
    curl_setopt_array($ch, [
        CURLOPT_URL            => $url,
        CURLOPT_RETURNTRANSFER => true,    // recuperer la reponse en string
        CURLOPT_TIMEOUT        => $this->timeout,

        CURLOPT_FOLLOWLOCATION => true,    // suit les redirects 301/302

        CURLOPT_ENCODING       => '',      // '' = accepte tous les encodings (gzip etc.)
    ]);

    // Execute la requete : retourne le HTML ou false
    $html = curl_exec($ch);

    // Lit le code HTTP (200, 404, 503, ...)
    $httpCode = (int) curl_getinfo($ch, CURLINFO_HTTP_CODE);

    // Si echec : recupere le message d'erreur
    $erreur = $html === false ? curl_error($ch) : null;

    // Ferme la session (libere les ressources)
    curl_close($ch);

    return [
        'html'      => $html ?: '',   // chaine vide si false
        'http_code' => $httpCode,
        'erreur'    => $erreur,
    ];
}

    // i = insensible a la casse, s = . match aussi \n
    if (!preg_match_all('#<tr[^>]*>(.*?)</tr>#is', $html, $rows)) {
        return $athletes;  // aucune ligne trouvee
    }

    // Dictionnaire des ids deja vus, pour dedupliquer
    $seen = [];

    // Boucle sur chaque <tr>
    foreach ($rows[1] as $rowHtml) {
        // Regex 2 : cherche le lien /athletes/123/...
        if (!preg_match('#/athletes/(\d+)#i', $rowHtml, $idMatch)) continue;

        $id = (int) $idMatch[1];

        // Skip si on a deja vu cet id dans cette page
        if (isset($seen[$id])) continue;
        $seen[$id] = true;

        // Regex 3 : decoupage des cellules <td>
        preg_match_all('#<td[^>]*>(.*?)</td>#is', $rowHtml, $cellsMatch);
        $cellsRaw = $cellsMatch[1] ?? [];

        // Nettoyage de chaque cellule (strip tags, decode entites)
        $cells = array_map([$this, 'cleanCell'], $cellsRaw);

        // Regex 4 : extraction du nom depuis le lien
        // Pattern : <a href="...athletes/123...">NOM PRENOM</a>
        $nom = '';
        if (preg_match(
            '#<a[^>]+href=["\'][^"\']*/athletes/' . $id
            . '[^"\']*["\'][^>]*>(.*?)</a>#is',
            $rowHtml, $nomMatch
        )) {
            $nom = $this->cleanCell($nomMatch[1]);
        }

        // Mapping positionnel (peut etre faux selon l'epreuve)
        $athletes[] = [
            'id'        => $id,
            'url_fiche' => "/athletes/$id/bilans",
            'rang'      => $cells[0] ?? '',
            'perf'      => $cells[1] ?? '',
            'nom'       => $nom !== '' ? $nom : ($cells[2] ?? ''),
            'club'      => $cells[3] ?? '',
            'ligue'     => $cells[4] ?? '',
            'dept'      => $cells[5] ?? '',
            'cat_an'    => $cells[6] ?? '',
            'date'      => $cells[7] ?? '',
            'lieu'      => $cells[8] ?? '',
            'cells'     => $cells,  // raw pour debug
        ];
    }
    return $athletes;
}

private function cleanCell($html) {
    // Etape 1 : remplacer <br> par des espaces (pour ne pas coller deux mots)
    $txt = preg_replace('#<br\s*/?>#i', ' ', $html);

    // Etape 2 : enlever toutes les balises HTML restantes
    $txt = strip_tags($txt);

    // Etape 3 : decoder les entites HTML (&amp; -> &, &eacute; -> e, etc.)
    $txt = html_entity_decode($txt, ENT_QUOTES | ENT_HTML5, 'UTF-8');

    // Etape 4 : normaliser les espaces multiples en un seul
    $txt = preg_replace('#\s+#u', ' ', $txt);

    // Etape 5 : retirer espaces en debut/fin
    return trim($txt);
}

Decision de design — pourquoi regex et pas DOMDocument ?

PHP offre DOMDocument qui parse proprement le HTML en arbre DOM. Pourquoi ne pas l'utiliser ?

  1. Athle.fr sert du HTML mal forme. Tags non fermes, attributs sans guillemets, encoding douteux. DOMDocument echoue ou emet des warnings deroutants.
  2. Performances. Sur des pages de 100 ko, la regex est plus rapide a executer que l'analyse DOM complete.
  3. Simplicite ciblee. On ne cherche que 4 patterns precis (tr, lien athlete, pagination, total). DOM serait surdimensionne.

Le compromis est connu : la regex est plus fragile si la mise en page change drastiquement. C'est precisement pour cela que test_page.php existe.

Mapping positionnel fragile. Le code suppose 9 cellules dans l'ordre rang/perf/nom/club/ligue/dept/cat_an/date/lieu. Athle.fr peut servir entre 7 et 10 cellules selon l'epreuve (vent en sprint/saut, lieu absent pour certains records). Si le mapping devient faux, la solution est d'ouvrir test_page.php, regarder la section "cellules brutes", et adapter le code.

HTTP 503 / Operation timed out. Athle.fr injoignable. analyze() retourne success=false et http_code renseigne. ScrapingRunner incremente fetch_errors.
HTTP 200 mais 0 athletes. La page existe mais son contenu a change. Symptome : compteur d'erreurs reste a zero mais athletes_inserts n'augmente plus. Ouvrir test_page.php pour comprendre.
Caracteres mal decodes. Accents qui sortent en "Ã©" au lieu de "e". Solution : verifier que la page est servie en UTF-8 et que html_entity_decode recoit 'UTF-8' comme charset.
Pagination introuvable. Sur la derniere page, le format peut differer. Le code retourne null pour total_pages, ScrapingRunner s'appuie alors sur page_total stocke en BDD.
Chapitre XI

Le chef d'orchestrelib/ScrapingRunner.php Phase 2

La piece maitresse. Elle ne fait pas le travail elle-meme — elle le coordonne. Cycles de vingt-cinq secondes, persistance sur disque, anti-ban a trois cents millisecondes.
ScrapingRunner reprend le pattern de l'ancien scraper.php du projet : flag de demarrage en fichier, progression sauvegardee a chaque etape, cycles bornes a vingt-cinq secondes pour respecter le timeout HTTP, et reprise possible apres un crash. Le fichier orchestre tout le monde — il interroge SourceTableReader pour les candidates, demande a UrlAnalyzer de construire chaque URL paginee, confie a PageAnalyzer le telechargement et l'extraction, et enfin INSERT chaque athlete trouve dans nom_et_liens. Entre deux fetches, une pause de trois cent millisecondes permet d'eviter le bannissement par athle.fr. La persistance se fait via trois fichiers du dossier state/, savamment articules. C'est la classe la plus longue (267 lignes) et la plus critique : un bug ici, et tout le pipeline s'arrete.

Pourquoi des cycles de 25 secondes ? Le serveur Hostinger impose un timeout de 30 secondes par requete HTTP. Si une page PHP met plus de 30 secondes a repondre, le serveur la tue. Plutot que de tout faire en une seule page (impossible vu le volume), on decoupe le travail en cycles de 25 secondes (marge de securite), et on recharge la page automatiquement entre chaque cycle. Le travail avance peu a peu, sans jamais depasser le timeout.

Qu'est-ce qu'un flag ? Un fichier simple dont la presence signifie "operation en cours". On peut le voir, le supprimer a la main, le creer. C'est plus pratique qu'une variable en BDD : aucun risque de transaction non commitee, lisibilite immediate via FTP/SSH.

Code commente — runCycle() (le coeur du scraping)

public function runCycle($maxSeconds = 25) {
    $progress = $this->getProgress();
    if (!$progress || !$this->isRunning()) return null;

    // Recharger la liste des candidates
    $cacheFile = $this->stateDir . '/' . $progress['cache_file'];
    if (!file_exists($cacheFile)) {
        // Anomalie : flag present mais cache disparu
        $progress['error'] = 'Cache candidates introuvable, relance start().';
        $progress['finished'] = true;
        $this->saveProgress($progress);
        $this->stop();
        return $progress;
    }
    $candidates = json_decode(file_get_contents($cacheFile), true);

    // Instancier les outils dont on a besoin
    require_once __DIR__ . '/PageAnalyzer.php';
    require_once __DIR__ . '/UrlAnalyzer.php';
    $pa = new PageAnalyzer();
    $ua = new UrlAnalyzer();

    // Preparer le statement (1 fois, reutilise pour toute la session)
    $stmt = $this->conn->prepare("INSERT INTO nom_et_liens (url) VALUES (?)");
    if (!$stmt) {
        $progress['error'] = 'Prepare INSERT failed: ' . $this->conn->error;
        $this->saveProgress($progress);
        return $progress;
    }

    $cycleStart = microtime(true);
    $cycleInserts = 0;
    $cyclePages   = 0;
    $logLines     = [];

    // Boucle principale : tant qu'on a du temps
    while ((microtime(true) - $cycleStart) < $maxSeconds) {

        // Plus de candidates ? on a fini
        if ($progress['url_index'] >= count($candidates)) {
            $progress['finished'] = true;
            $progress['last_action_at'] = date('Y-m-d H:i:s');
            $this->saveProgress($progress);
            $this->stop();
            $logLines[] = 'TERMINE';
            break;
        }

        // Candidate courante + page courante
        $cur       = $candidates[$progress['url_index']];
        $pageTotal = max(1, (int)$cur['page_total']);
        $page      = (int)$progress['page_courante'];

        // Construire l'URL pour cette page precise
        $urlPage   = $ua->urlPourPage($cur['url'], $page);

        // Fetch + parse
        $r = $pa->analyze($urlPage);
        $progress['last_url'] = $urlPage;
        $progress['last_action_at'] = date('Y-m-d H:i:s');

        if (!$r['success']) {
            // Echec du fetch : on incremente l'erreur et on passe
            $progress['stats']['fetch_errors']++;
            $logLines[] = "FETCH KO #{$cur['id']} p$page (HTTP {$r['http_code']})";
        } else {
            // Succes : INSERT chaque athlete
            $nbInsertsPage = 0;
            foreach ($r['athletes'] as $a) {
                $url = "https://athle.fr" . $a['url_fiche'];
                $stmt->bind_param('s', $url);
                if ($stmt->execute()) {
                    $nbInsertsPage++;
                    $progress['stats']['athletes_inserts']++;
                }
            }
            $logLines[] = "OK #{$cur['id']} p$page → {$nbInsertsPage} INSERT";
            $cycleInserts += $nbInsertsPage;
        }
        $cyclePages++;
        $progress['stats']['pages_traitees']++;

        // Avancer : prochaine page ou prochaine URL ?
        if ($page >= $pageTotal) {
            $progress['url_index']++;
            $progress['page_courante'] = 1;
            $progress['stats']['urls_terminees']++;
        } else {
            $progress['page_courante'] = $page + 1;
        }

        // Sauvegarder l'etat APRES chaque page (reprise apres crash)
        $this->saveProgress($progress);

        // Anti-ban : pause 300ms avant le prochain fetch
        if ((microtime(true) - $cycleStart) < $maxSeconds) {
            usleep($this->delayUs);
        }
    }

    $stmt->close();

    return [
        'progress'      => $progress,
        'cycle_pages'   => $cyclePages,
        'cycle_inserts' => $cycleInserts,
        'duree_s'       => round(microtime(true) - $cycleStart, 1),
        'log'           => $logLines,
    ];
}

Decision de design 1 — INSERT brut sans IGNORE

Le code utilise INSERT INTO nom_et_liens (url) VALUES (?) sans aucune precaution anti-doublon. Pourquoi ?

  1. Performance. Tester avant chaque INSERT que l'URL n'existe pas couterait une SELECT additionnelle — doublement du temps.
  2. Robustesse. Aucune contrainte UNIQUE = aucune erreur SQL possible. Le pipeline ne s'arrete jamais sur une erreur d'unicite.
  3. Separation des responsabilites. Inserer est le job du runner. Dedupliquer est le job de cleanup_duplicates.php. Les deux sont independants.

Le compromis : un peu de place disque perdue temporairement, en echange d'un pipeline a tolerance d'erreur maximale.

Decision de design 2 — figer les candidates

Pourquoi ecrire les candidates dans un fichier JSON plutot que de relire la BDD a chaque cycle ?

  1. Determinisme de l'index. Si on relisait la BDD, url_index = 17 pourrait pointer sur des candidates differentes selon que des lignes ont ete ajoutees ou supprimees entre deux cycles. Le snapshot fige garantit que 17 est toujours 17.
  2. Reprise apres crash. Si le serveur plante au milieu d'un cycle, on relit progress.json et le cache — on reprend exactement ou on s'est arrete.
  3. Performance. Lire un JSON sur disque est plus rapide que rejouer la requete SQL filtree.

Decision de design 3 — delay 300ms entre fetches

Pourquoi 300 millisecondes ?

  1. Trop court (10ms) : athle.fr nous detecte comme bot, nous bannit temporairement.
  2. Trop long (5 secondes) : on n'avance pas assez vite, le scraping prendrait des semaines.
  3. 300ms = environ 3 requetes par seconde = volume comparable a un humain rapide qui naviguerait le site.

Cette valeur a ete trouvee empiriquement. Si athle.fr durcit ses protections, il faudra l'augmenter.

Chaque methode decode*() d'UrlAnalyzer lit $this->referentiel['parametres'][$cle]['valeurs'][$value], et tombe en fallback "Inconnu (X)" si la cle ou la valeur n'existe pas. Le fichier est charge une seule fois au constructeur et reste en memoire jusqu'a la fin de la requete HTTP.

Ajouter une nouvelle valeur — exemple

Supposons qu'athle.fr ajoute une categorie "U23" (espoir mais sous une autre denomination). Pour la reconnaitre :

"frmcategorie": {
  "valeurs": {
    "SE": "Senior",
    "ES": "Espoir",
    "U23": "Moins de 23 ans",  <-- AJOUTER CETTE LIGNE
    ...
  }
}

Sauvegarder, recharger la page. UrlAnalyzer affichera desormais "Moins de 23 ans" partout ou il rencontrera frmcategorie=U23.

Cas d'erreur possibles

JSON malforme (virgule manquante, accolade en trop). json_decode retourne null. UrlAnalyzer tombe systematiquement en "Inconnu (X)". Solution : valider le JSON sur jsonlint.com avant sauvegarde.
Fichier absent ou non lisible. file_get_contents retourne false, UrlAnalyzer echoue silencieusement. Solution : verifier les permissions et l'existence via diagnose.php.

Chapitre XV

Le dossier state/ est la memoire du systeme. Comprendre ses cinq fichiers, c'est comprendre comment le scraping survit aux interruptions.
Le seul lieu d'ecriture sur disque, hors BDD, est le dossier state/. Decision de design — pourquoi 3 fichiers separes ?

  1. Flag separe. Permet d'arreter le scraping par simple rm flag — meme depuis FTP/SSH si l'interface est inaccessible. Pas besoin de toucher au JSON delicat.
  2. Progress separe. Lisible et modifiable a la main. On peut decaler url_index de force pour sauter un blocage, par exemple.
  3. Candidates separe. Fichier volumineux (potentiellement plusieurs Mo). Le garder a part evite de le reecrire a chaque sauvegarde de progress.

Pourquoi geler les candidates ?

Si l'on relisait la BDD a chaque cycle, l'index dans la liste pourrait se decaler si une ligne etait inseree ou supprimee. En figeant le snapshot au moment du start, on garantit que url_index = 17 pointera toujours sur la meme URL — et la reprise apres crash devient deterministe. Si quelqu'un ajoute une nouvelle table source pendant un scraping en cours, elle sera ignoree jusqu'au prochain start, ce qui est exactement le comportement souhaite.

Permissions sur Hostinger

Le dossier state/ doit avoir les droits d'ecriture par PHP. Sur Hostinger :

  • Via File Manager : clic droit sur le dossier → "Modifier les permissions" → 755 ou 777.
  • Via FTP : commande SITE CHMOD 755 state.
  • Via SSH (si dispo) : chmod 755 state/.

Le code essaie aussi @mkdir($stateDir, 0755, true) au constructeur, mais si le dossier parent n'autorise pas la creation, l'operation echoue silencieusement (le @ supprime le warning).

Recuperation manuelle apres crash

Si le scraping s'est interrompu brutalement (timeout, deconnexion, redemarrage serveur), au prochain GET sur index.php :

  1. Le flag existe encore : runCycle entre dans la boucle.
  2. Le progress.json est lu : url_index et page_courante ont les valeurs d'avant le crash.
  3. Le cache candidates est intact (il n'a pas ete modifie depuis le start).
  4. Le scraping reprend exactement ou il s'est arrete — au pire on perd la page en cours.

C'est la beaute de la persistance par fichiers : aucune transaction BDD a gerer, aucun rollback complexe.
